# Agile Software Development: Sprint Review and Retrospective

This repository contains the Sprint Review and Retrospective deliverable from my software development coursework. The artifact highlights my experience transitioning a development team from a traditional Waterfall model to a Scrum-Agile framework for a pilot application project (SNHU Travel). 

## Portfolio Reflection

How do I interpret user needs and implement them into a program? How does creating “user stories” help with this?
Interpreting user needs requires shifting the focus from technical specifications to the actual value the end-user expects. Creating "user stories" is highly effective for this because it breaks down monolithic, vague requirements into actionable, bite-sized tasks written from the user's perspective (e.g., "As a user, I want to filter flights by price, so I can find affordable travel options"). This format ensures the development team understands the why behind a feature, making it easier to write code that directly solves the customer's problem without over-engineering the solution.

How do I approach developing programs? What Agile processes do I hope to incorporate into my future development work?
I approach development iteratively. Rather than trying to map out a massive project from start to finish and waiting months for a deliverable, I prefer to build, test, and refine in smaller, manageable increments. Moving forward in my career, I plan to incorporate several Agile processes into my personal and professional development workflows: Kanban boards (like Jira) for clear visual tracking, planning poker for realistic time estimations, and Sprint Retrospectives to ensure continuous process improvement after a major release. 

What does it mean to be a good team member in software development?
Being a good team member requires radical transparency and proactive communication. It involves speaking up immediately during a daily standup when blocked—rather than hiding struggles—so the team can pivot, pair-program, or assist. In an Agile environment, it also means adapting to changing client requirements with flexibility rather than frustration, and maintaining a shared sense of ownership over the final product increment.
